소규모 사무실을 위한 Django 업무관리 시스템 직접 만들기

SaaS 대신 직접 만들었다. 강사 파견 업체의 업무 흐름 전체를 Django 하나로 묶은 과정과 설계 결정들을 정리했다.

  • Python
  • Django
  • PostgreSQL
  • ERP
  • 권한 설계
  • Windows Server

1. 시작하게 된 문제

강사 파견·교육 사업을 운영하는 소규모 사무실에는 생각보다 많은 데이터가 흐른다.

  • 어떤 업무가 누구에게 요청됐고, 지금 어느 단계인가
  • 강사에게 이번 달 얼마를 줘야 하는가, 유류비와 식대 공제는 어떻게 반영할 것인가
  • 직원 식사는 누가 몇 번 먹었고, 아직 못 낸 금액은 얼마인가
  • 이달 수입·지출 합계는 얼마이고, 어떤 항목에서 발생했는가

사무실에서는 이 흐름을 엑셀과 카카오톡으로 관리하고 있었다. 버전이 관리되지 않고, 결재선이 없고, 숫자가 어디서 왔는지 추적하기 어려웠다. 기성 그룹웨어는 기능이 너무 많거나 비용이 맞지 않았다. 그래서 직접 만들기로 했다.

2. 프로그램이 해결하려는 일

한 줄로 정리하면 엑셀과 구두 보고를 코드로 대체하는 것이다.

구체적으로는 다음 흐름을 시스템 안에서 처리하게 하려 했다.

  1. 직원이 업무를 요청하면 부서장, 본부장, 대표 순으로 결재한다.
  2. 강사 파견이 확정되면 강사료 명세서를 만들고, 입금 확인 후 회계 항목을 자동 생성한다.
  3. 매월 식대를 개인별 통장 잔고처럼 적립·차감하고, 미납 금액은 자동 이월한다.
  4. 수입·지출을 월별로 집계해 대표 대시보드에 그래프로 표시한다.

3. 전체 구조

config/             # Django 설정, URL 라우터
apps/
  accounts/         # 사용자·역할(Role) 모델
  organization/     # 부서 모델
  workitems/        # 업무 요청·상태 전이
  approvals/        # 결재 액션
  accounting/       # 수입·지출, 예산
  audit/            # 관리자 뷰, 감사 로그
  notifications/    # 이메일 알림
  modules/
    schedule/       # 일정·캘린더 (FullCalendar)
    meal_ledger/    # 식사 장부 (통장식 잔고)
    business/       # 사업 문의·파이프라인
    instructor_fee/ # 강사료 신청·지급
    business_trip/  # 출장비
    work_report/    # 일일·주간 업무 보고
    weekly_plan/    # 주간 계획표
templates/          # Django 템플릿 (base.html 공통 레이아웃)
run_production.py   # cheroot WSGI 서버 (HTTPS, 포트 443)

기술 스택은 Django 5.2 + PostgreSQL + Python 3.x이다. 프론트엔드는 별도 프레임워크 없이 Django 템플릿에 Tailwind CSS CDN과 일부 React 18(Babel standalone)을 조합했다. React는 상태 전이가 복잡한 식사 장부 화면에만 제한적으로 사용했다.

4. 역할 기반 접근 제어

사용자 한 명에게 역할(Role) 하나가 부여된다. SUPER_ADMIN > ADMIN > CEO > MANAGER > DEPT_LEAD > STAFF 순의 계층이 있고, INSTRUCTOR, ACCOUNTANT 등 기능별 역할도 별도로 존재한다.

class Role(models.TextChoices):
    SUPER_ADMIN = 'SUPER_ADMIN', '시스템 최고관리자'
    ADMIN       = 'ADMIN',       '시스템 운영관리자'
    CEO         = 'CEO',         '대표'
    MANAGER     = 'MANAGER',     '본부장'
    DEPT_LEAD   = 'DEPT_LEAD',   '부서 책임자'
    STAFF       = 'STAFF',       '직원'
    INSTRUCTOR  = 'INSTRUCTOR',  '강사'
    ...

뷰마다 데코레이터(@admin_required, @admin_or_ceo_required)나 인라인 권한 검사로 접근을 제한했다. 역할이 많아질수록 분기 조건이 복잡해지는 것이 이 구조의 가장 큰 단점이다.

5. 식사 장부: 통장식 잔고 모델

초기 설계는 paid_amount(입금액)와 carryover(이월액)를 월별로 개별 저장하는 방식이었다. 문제는 “전달 미납이 얼마인지”를 계산하려면 그 달부터 역순으로 체인을 타야 한다는 것이었다. 코드가 복잡해졌고, 값이 하나라도 잘못되면 이후 달 전체가 틀렸다.

그래서 모델을 다음처럼 재설계했다.

잔고 = (지금까지 누적 입금) - (지금까지 누적 식사 횟수 * 단가)

MealDeposit 모델을 별도로 만들어 입금 거래를 한 건씩 기록한다. 전월 잔고는 별도로 저장하지 않는다. 항상 누적값에서 역산하면 된다.

dep_total    = MealDeposit.objects.filter(member=member, date__lte=end).aggregate(s=Sum('amount'))['s'] or 0
meal_total   = MealRecord.objects.filter(member=member, date__lte=end).count()
balance      = dep_total - meal_total * price
prev_balance = balance - deposit_this_month + cost_this_month

이 구조는 이월 계산 버그가 구조적으로 발생하기 어렵고, “지금까지 총 얼마를 냈고 얼마치를 먹었는가”를 쿼리 두 줄로 답할 수 있다.

6. 운영 서버: cheroot + WhiteNoise

Django 개발 서버(runserver_plus)는 파일 변경을 감지하면 자동 재시작한다. 개발 중에는 편리하지만 사무실 내부 도메인으로 서비스할 때 예고 없이 끊기는 문제가 있었다.

운영에서는 cheroot WSGI 서버로 전환했다. 파일 감시 기능이 없어 재시작이 발생하지 않고, 멀티스레드 설정으로 동시 요청도 처리할 수 있다. WhiteNoise는 정적 파일을 Django 미들웨어 레벨에서 직접 서빙하기 위해 추가했다.

server = Server((HOST, 443), application, numthreads=12, request_queue_size=50)
server.ssl_adapter = BuiltinSSLAdapter(cert, key)
server.start()

Windows 환경이라 .bat 파일로 서버를 기동한다. 배치 파일에 한글이 들어가면 파싱 오류가 발생해서 파일 전체를 ASCII로만 작성해야 했다.

7. 계정 삭제: 소프트 삭제

초기에는 계정 삭제를 user.delete()로 구현했다. 업무 이력·결재 기록이 있는 계정은 Django의 PROTECT 제약으로 삭제가 차단됐고, 에러 메시지만 뜨는 상황이었다.

해결 방법은 단순하다. 삭제하지 않고 숨긴다.

target.is_active = False
target.save(update_fields=['is_active'])

User.is_active=False는 로그인도 차단하고, 목록 조회 시 filter(is_active=True)로 제외하면 화면에서도 사라진다. 데이터는 보존되어 회계·감사 추적이 끊기지 않는다.

8. 설계하면서 신경 쓴 점

모듈 분리: 기능마다 apps/modules/ 아래에 독립 앱을 만들었다. 각 앱은 자기 모델·뷰·URL을 가진다. 식사 장부를 전면 재설계할 때 다른 모듈을 건드리지 않아도 됐다.

회계 자동 연동: 강사료 입금 확인, 식대 집계 등 수작업이 필요했던 회계 항목을 이벤트 발생 시점에 자동 생성하도록 연결했다. 단, 동기화 로직이 뷰에 직접 들어가 있어서 테스트하기 어렵다는 구조적 한계가 있다.

민감 정보 노출 방지: 계정 삭제 확인 창, 임시 비밀번호 발급 결과 등 민감 정보를 화면에 오래 노출하지 않도록 Django messages 프레임워크를 활용했다.

9. 어려웠던 점과 해결 방법

Cloudflare 522 오류: 도메인으로 접속할 때 간헐적으로 연결 시간 초과가 발생했다. 원인은 HTTPS 서버가 실행 중이지 않은 것이었다. 배치 파일 실행 오류로 서버가 뜨지 않았고, Cloudflare가 오리진에 연결하지 못해 522를 반환했다. 배치 파일 인코딩 문제를 해결하고 서버 기동 로그를 확인하는 습관을 들이게 됐다.

월간 정산 이월 버그: 월별 미납을 체인으로 계산하는 방식은 중간 값이 하나라도 잘못 저장되면 이후 달 전체가 틀렸다. 누적합 방식으로 재설계하면서 해결했다. 설계 단계에서 “어떤 값을 저장하고 어떤 값을 계산할 것인가”를 명확히 하는 것이 중요하다는 걸 실감했다.

기존 데이터 마이그레이션: 모델을 재설계하면 기존 DB의 paid_amount 데이터가 새 구조와 맞지 않았다. MealMonthlySettlement.paid_amount에 남아 있는 이전 입금 기록을 MealDeposit으로 옮기는 마이그레이션 스크립트를 별도로 작성해 처리했다.

10. 현재 한계와 다음 개선 방향

아직 남아 있는 한계도 솔직하게 정리하면 다음과 같다.

  • 테스트 코드가 없다. 기능 추가·수정 시 회귀 버그를 수동으로 확인해야 한다.
  • 회계 동기화 로직이 뷰에 인라인으로 들어가 있어, 서비스 레이어로 분리하지 못했다.
  • 운영 서버를 Windows에서 직접 실행하는 방식이라 프로세스 재시작 자동화가 되어 있지 않다.

작은 사무실 하나가 엑셀에서 벗어나게 하는 것이 목표였고, 그 부분은 동작하고 있다. 다음 단계는 테스트 커버리지를 올리는 것이다.
