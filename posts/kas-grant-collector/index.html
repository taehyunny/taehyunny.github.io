정부지원사업 공고를 의사결정 자료로 바꾸는 업무 흐름 설계

정부지원사업, 입찰, 강사 모집 공고를 수집한 뒤 정규화, 중복 제거, 점수화, 보고서 생성으로 이어지게 만들어 사람이 검토할 후보를 줄인 업무 자동화 기록입니다.

  • 사업기획
  • 공공데이터
  • AI 자동화
  • 데이터 기반 의사결정

1. 어떤 업무 문제에서 시작했는가

정부지원사업이나 공모, 입찰 정보는 여러 사이트에 흩어져 있다. 기업마당, K-Startup, 나라장터, 나라일터, 교육청 게시판, 지자체 공지사항처럼 각각 보는 위치도 다르고 공고의 성격도 다르다.

문제는 단순히 “공고를 많이 모으는 것”이 아니었다. KAS가 실제로 관심 있는 분야는 농업교육, 강사 출강, 위탁교육, 콘텐츠, 전자출판, CBT, 신생기업 지원금처럼 비교적 좁고 구체적이다. 그래서 일반적인 지원사업 목록을 그대로 보면 관련 없어 보이는 공고가 너무 많이 섞였다.

초기에는 농업, 교육, 콘텐츠 같은 키워드만으로 점수를 주면 될 것이라고 생각했다. 하지만 실제로는 교육생 모집, 박람회 참가기업 모집, 단순 물품 구매, 지역이 맞지 않는 지원금, 개인 강사만 가능한 공고가 같이 올라왔다. 이 때문에 “우리 회사가 신청할 수 있는가”, “강사 매칭 사업과 연결되는가”, “지원금으로 봐야 하는가”, “시장조사 참고자료로만 봐야 하는가”를 나누는 기준이 필요했다.

2. 문제를 어떻게 정의했는가

이 프로그램의 목적은 KAS가 확인해야 할 공고를 자동으로 모으고, 회사 관점에서 우선순위를 정리하는 것이다.

주요 목표는 다음과 같다.

  • 여러 API와 게시판에서 공고 데이터를 수집한다.
  • 서로 다른 응답 형식을 공통 스키마로 정규화한다.
  • 제목, 기관, 마감일 기준으로 중복 공고를 제거한다.
  • 마감일, 지역, 사업 분야, 수행 역할, 법인 가능성 등을 기준으로 점수를 계산한다.
  • 강사 매칭, 교육운영 수주, 회사 지원금, 시장조사 참고자료를 구분한다.
  • 결과를 CSV, Excel, Markdown, HTML 보고서로 출력한다.
  • 브라우저 기반 콘솔에서 수집 실행, 조건 설정, 결과 확인을 할 수 있게 한다.

현재 구현은 “완전 자동으로 최종 판단”하기보다는, 사람이 검토해야 할 후보를 줄이는 데 초점을 두고 있다. 특히 공고문과 첨부파일 분석은 법인 신청 가능 여부, 지역 제한, 제출서류, 실적 조건을 확인하기 위한 보조 단계로 설계했다.

3. 데이터는 어떤 흐름으로 정리되는가

프로젝트는 크게 수집, 정규화, 분류/점수화, 보고서 출력, 브라우저 콘솔로 나뉜다.

src/
  collectors/        # API 및 게시판 수집기
  main.py            # 전체 실행 흐름
  normalizer.py      # 공통 스키마 변환과 중복 제거
  scoring.py         # 기본 적합도 점수 계산
  *_classifier.py    # 교육, 강사, 지원금, 카테고리 분류
  *_reporter.py      # CSV, Excel, Markdown 보고서 출력
  document_mirror.py # 첨부파일 및 상세 공고문 분석
  crawl_guard.py     # 안전 크롤링 제어

app/
  server.py          # 로컬 브라우저 앱 서버
  static/
    index.html
    app.js
    styles.css

data/
  raw/               # 원본 응답 저장
  output/            # 최종 결과 파일

수집 대상은 공식 API와 일부 게시판 수집기를 함께 사용한다. README 기준으로 기업마당, K-Startup, 나라장터 입찰/사전규격/낙찰/계약, 누리장터, 나라일터, 전라남도교육청 외부강사 게시판, 지역 농업/교육/기관 게시판 수집기가 포함되어 있다.

브라우저 콘솔은 app/server.py에서 제공한다. 이 앱은 정적 UI처럼 보이지만 내부적으로는 로컬 서버 API를 호출해 현재 결과 요약, 상세 설정, 수집 실행, 결과 파일 목록을 보여준다. 최근에는 간단한 비밀번호 로그인과 관리자/보기 전용 권한도 추가했다.

4. 수집 결과를 어떻게 판단 자료로 바꾸는가

실행 진입점은 python -m src.main이다. 전체 흐름은 다음 순서로 진행된다.

  1. 환경 변수와 실행 옵션을 읽는다.
  2. 출력 폴더와 원본 저장 폴더를 준비한다.
  3. 안전 크롤링 설정을 적용한다.
  4. API와 게시판 수집기를 실행한다.
  5. 원본 응답을 data/raw/에 저장한다.
  6. 각 소스의 응답을 공통 필드로 정규화한다.
  7. 제목, 기관, 마감일 기준으로 중복 제거를 한다.
  8. 마감일 조건으로 공고를 필터링한다.
  9. KAS 기준 점수를 계산한다.
  10. 교육 수주, 강사 매칭, 지원금, 카테고리, 플랫폼 전략 분류를 적용한다.
  11. 선택적으로 공고문과 첨부파일을 분석한다.
  12. 회사 자료와 공고 조건을 비교한다.
  13. CSV, Excel, Markdown, HTML, PDF 형태의 결과물을 만든다.

점수 체계는 단일 점수 하나에 모든 의미를 넣지 않도록 나누었다. 예를 들어 농업 관련성은 높지만 교육 수행 역할이 없으면 직접 수주 후보로 올리기 어렵다. 반대로 강사 모집 공고는 회사가 직접 신청하는 지원금은 아니지만 강사 매칭 리드로는 중요할 수 있다.

그래서 현재는 다음과 같은 관점으로 나누어 본다.

  • 농업, 곤충, 유기농, 생태교육 등 도메인 적합도
  • 강사 출강, 위탁교육, 교육운영, 콘텐츠 제작 등 수행 역할
  • 전남, 전북, 나주 등 지역 우선순위
  • 법인, 주식회사, 중소기업 신청 가능성
  • 공고문/첨부 분석 여부와 제출서류 조건
  • 교육생 모집, 개인 전용, 지역 외 공고 같은 감점 요소

브라우저 앱에서는 이 결과를 다시 “수주/강사 매칭”과 “지원금/회사 혜택”으로 나누어 보여준다. 같은 공고라도 어떤 관점에서 봐야 하는지 다르기 때문에, 한 화면에서 두 축을 분리해서 보는 구조로 정리했다.

5. 자동화와 사람 검토를 어떻게 나눴는가

첫 번째로 신경 쓴 부분은 API 키와 민감정보를 코드에 넣지 않는 것이다. 기업마당, 공공데이터포털, OpenAI, Ollama 설정은 .env에서 읽도록 했다. 브라우저 앱도 관리자와 보기 전용 계정을 나누고, 보기 전용 사용자는 원본 CSV 다운로드나 수집 실행을 할 수 없도록 막았다.

두 번째는 수집 실패가 전체 실행을 멈추지 않게 하는 것이다. 정부 API나 기관 게시판은 응답 형식이 달라질 수 있고, 일시적으로 403이나 429가 발생할 수도 있다. 그래서 수집기별 예외를 잡고, 실패한 소스는 빈 목록으로 처리한 뒤 나머지 수집과 보고서 생성을 계속 진행하도록 했다.

세 번째는 정규화 계층을 둔 것이다. 각 API의 필드명이 다르기 때문에, 이후 점수화 로직이 원본 필드에 직접 의존하면 유지보수가 어려워진다. normalizer.py에서 source, title, organization, region, category, target, description, start_date, end_date, apply_url, contact, raw 같은 공통 필드로 변환한 뒤 다음 단계로 넘긴다.

네 번째는 크롤링을 공격적으로 하지 않는 것이다. 외부 게시판은 API가 아니라 HTML을 읽어야 하는 경우가 있으므로 캐시, 요청 지연, 사이트별 상세 조회 제한, 403/429 발생 시 해당 호스트 중단 같은 방어적인 규칙을 넣었다. 이 프로그램은 대량 크롤러가 아니라 업무 보조용 수집기이기 때문에, 느리더라도 안전하게 도는 편이 맞다고 판단했다.

다섯 번째는 결과물을 여러 형태로 내보내는 것이다. 개발자는 CSV와 Excel이 편하지만, 실제 업무 보고에는 Markdown, HTML, PDF가 더 적합할 때가 있다. 그래서 전체 결과 파일뿐 아니라 우선순위 보고서, 강사 기회 보고서, 제출자격 분석 보고서, A4 한 장 보고서를 따로 생성하도록 했다.

6. 구현하면서 드러난 문제

가장 어려웠던 점은 “관련 있어 보이는 공고”와 “실제로 KAS가 움직일 만한 공고”를 구분하는 일이었다. 예를 들어 농업이라는 단어가 들어가도 교육생 모집이면 KAS가 수주할 공고가 아니다. 반대로 강사 모집 공고는 회사가 직접 지원금을 받는 구조는 아니지만, 강사 매칭 사업에는 중요한 신호가 될 수 있다.

이를 해결하기 위해 공고를 하나의 등급으로만 보지 않고, 강사 매칭, 교육운영 수주, 회사 지원금, 시장조사 참고자료처럼 성격을 나누었다. 또한 학생 모집, 단순 박람회 참가, 물품 구매, 시설공사 같은 오탐 키워드는 감점하거나 별도 참고자료로 분리했다.

두 번째 어려움은 지역 정보였다. 일부 API는 지역 필드가 비어 있거나, 본문 안에만 지역 제한이 들어 있다. 그래서 현재는 지역 키워드와 기관명, 설명 필드를 함께 보고 전남, 전북, 나주 우선순위를 계산한다. 다만 지역 제한이 첨부파일에만 있는 경우는 아직 완전히 자동화하기 어렵기 때문에, 공고문/첨부파일 분석을 함께 보강하는 방향으로 잡았다.

세 번째는 S등급 기준이었다. 초기에는 키워드가 많이 맞으면 S등급이 쉽게 나왔다. 하지만 실제 검토를 해보니 화순, 서울, 제주처럼 KAS의 우선 지역과 거리가 있는 공고나, 콘텐츠 제작 용역처럼 농업교육과 약하게만 연결되는 공고도 상위에 올라왔다. 이후 직접 수주 후보는 농업·곤충·유기농·생태교육 같은 도메인과 강사/교육운영 역할을 함께 만족해야 높은 등급을 받을 수 있도록 기준을 강화했다.

네 번째는 보고서와 앱의 사용자 권한이었다. 원본 CSV에는 내부 분석 결과와 원본 데이터가 포함되므로 팀원에게 그대로 공유하기 애매했다. 그래서 관리자만 수집 실행과 상세 설정, 원본 CSV 다운로드를 할 수 있게 하고, 팀원은 보기 전용으로 대시보드와 보고서 중심으로 확인하도록 나누었다.

7. 한계와 다음 검증

아직 개선할 부분도 남아 있다. 특히 전남·전북 학교지원센터, 대학 평생교육원, 산림교육, 환경교육, 생태교육 기관 게시판은 더 확장할 필요가 있다. 또한 공고문 첨부파일을 더 안정적으로 읽어 법인 신청 가능 여부, 제출서류, 실적 조건을 자동으로 판단하는 부분도 계속 보강해야 한다.

이 프로젝트는 처음부터 완성된 서비스라기보다, 실제 업무에서 반복적으로 겪는 “공고 찾기와 1차 판단”을 자동화해보는 과정이었다. 지금 단계에서는 후보를 완벽하게 결정하기보다, 사람이 검토해야 할 목록을 줄이고 왜 추천됐는지 설명하는 데 초점을 맞추고 있다.

8. 다시 생각한 점

이 자동 수집기는 KAS가 관심 있는 공고를 더 빠르게 찾기 위한 업무 보조 도구다. 중요한 것은 모든 판단을 자동화하는 것이 아니라, 사람이 검토해야 할 후보를 줄이고 추천 이유를 설명할 수 있게 만드는 것이다.

정부지원사업과 입찰 정보는 계속 바뀌고, 공고마다 조건도 다르다. 그래서 이 프로그램은 수집, 정규화, 점수화, 보고서 생성이라는 반복 흐름을 자동화하되, 최종 신청 가능 여부와 사업 전략 판단은 사람이 확인하는 구조로 두었다.
