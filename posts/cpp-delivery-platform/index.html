주문·결제 데이터가 흔들리지 않게 서버 기준을 세운 기록

배달 플랫폼 프로젝트에서 주소, 주문, 결제, 리뷰 흐름을 서버와 데이터베이스 기준으로 검증하고, 주문 당시의 정보를 스냅샷으로 남기도록 설계한 기록입니다.

1. 어떤 운영 문제에서 시작했는가

자영업을 운영하며 주문, 결제, 고객 정보가 실제 운영 판단에 중요한 기준이 된다는 것을 경험했습니다. 하지만 데이터가 명확하게 기록되지 않거나 플랫폼 내부 흐름이 불투명하면 운영자는 감에 의존해 판단할 수밖에 없습니다.

이 프로젝트는 단순히 주문을 전달하는 배달 앱을 만드는 것보다, 주문과 결제 데이터가 신뢰할 수 있는 방식으로 저장되고 검증되는 구조를 만드는 데 초점을 두었습니다.

3. 사용자는 어떤 흐름을 지나가는가

사용자는 주소를 검색하고, 저장된 주소 중 주문에 사용할 주소를 선택합니다. 이후 가게와 메뉴를 조회하고, 주문을 생성한 뒤 결제 내역과 영수증을 확인합니다.

주소 검색
→ 주소 선택 및 관리
→ 가게 상세 / 메뉴 조회
→ 주문 생성
→ 결제 내역 및 영수증 확인

이 흐름에서 중요한 것은 사용자가 보는 화면보다, 주소·주문·결제 데이터가 서버와 데이터베이스에서 일관되게 연결되는 구조였습니다.

4. 어떤 데이터가 기준이 되어야 하는가

4-1. 주소 관리

사용자가 여러 주소를 저장하고, 현재 주문에 사용할 주소를 선택할 수 있도록 주소 관리 기능을 구성했습니다. 주소 데이터는 주문 생성 시 배달 주소와 연결되며, 영수증과 과거 주문 내역에서도 확인할 수 있도록 흐름을 설계했습니다.

주요 기능은 다음과 같습니다.

  • 도로명 / 건물명 기반 주소 검색
  • 집, 회사, 기타 주소 분류
  • 현재 선택된 기본 주소 표시
  • 주문 내역 및 영수증과 배달 주소 연결

4-2. 가게 상세 및 메뉴 조회

가게 상세 화면에서는 영업시간, 최소 주문 금액, 배달 정보, 메뉴 정보를 확인할 수 있도록 구성했습니다. 가게 정보와 메뉴 정보는 주문 생성 시 필요한 기준 데이터가 되므로, 서버와 DB에서 분리해 관리했습니다.

4-3. 리뷰 및 사장님 답글

리뷰 기능은 사용자의 주문 경험이 다시 가게 운영 데이터로 이어지는 흐름을 보여주는 기능입니다. 사용자 리뷰와 사장님 답글을 분리해 관리하고, 메뉴별 리뷰를 확인할 수 있도록 구성했습니다.

5. 시스템은 어떤 구조로 검증하는가

배달 플랫폼에서는 클라이언트가 전달한 값만으로 주문과 결제를 처리하면 데이터가 쉽게 오염될 수 있다고 판단했습니다. 따라서 클라이언트 요청은 C++ TCP 서버를 거쳐 처리되고, 서버가 MariaDB의 기준 데이터를 조회해 주문과 결제 정보를 검증하는 구조로 설계했습니다.

통신 구조

팀원들이 같은 방식으로 요청과 응답을 주고받을 수 있도록 공통 프로토콜 규칙을 정리했습니다.

Signature 2 Bytes
CmdID 2 Bytes
BodySize 4 Bytes
JSON Body Variable

이 구조를 통해 요청의 종류와 데이터 크기를 명확히 구분하고, 이후 JSON Body를 파싱해 기능별 로직으로 연결할 수 있도록 했습니다.

6. 내가 맡은 설계 역할

팀장 및 서버 담당으로 참여했습니다. 서버 구조와 DB 연동 흐름을 설계하고, 주문·결제·주소·리뷰 기능이 같은 데이터 기준으로 연결되도록 조율했습니다.

특히 팀원 간 통신 기준이 달라지지 않도록 요청/응답 구조를 README에 정리하고, DTO 참조 방식을 문서화했습니다.

7. 구현하면서 드러난 문제

문제 1. 메뉴 정보 변경 시 과거 주문 데이터가 흔들리는 문제

메뉴 가격이나 옵션이 수정되면, 과거 주문 내역이 현재 메뉴 정보를 따라 바뀔 수 있는 위험이 있었습니다. 주문 내역은 결제와 영수증의 기준이 되기 때문에, 이 데이터가 변경되면 서비스 신뢰도에 영향을 줄 수 있다고 판단했습니다.

이를 해결하기 위해 주문 시점의 메뉴명, 가격, 옵션 정보를 주문 상세 데이터로 저장하는 스냅샷 구조를 적용했습니다.

결과적으로 현재 메뉴 정보와 과거 주문 이력을 분리해, 주문 당시 기준의 영수증 데이터를 유지할 수 있도록 했습니다.

문제 2. 팀원 간 통신 기준이 달라질 수 있는 문제

프론트엔드, 서버, DB 담당자가 각자 다른 기준으로 요청/응답 구조를 생각하면 기능 연동 과정에서 충돌이 발생할 수 있었습니다.

이를 해결하기 위해 8바이트 헤더와 JSON Body 기반의 공통 프로토콜 규칙을 README에 정리했습니다. 덕분에 팀원들이 같은 통신 규칙을 기준으로 기능을 구현할 수 있었고, 서버 담당자로서 각 파트의 흐름을 조율할 수 있었습니다.

8. 이 구조에서 배운 점

이 프로젝트를 통해 백엔드 개발은 단순히 데이터를 저장하고 응답을 반환하는 일이 아니라, 서비스의 신뢰 기준을 설계하는 일이라는 것을 배웠습니다.

특히 주문과 결제처럼 사용자 신뢰와 직접 연결되는 데이터는 클라이언트 요청값에만 의존해서는 안 되며, 서버와 데이터베이스 기준으로 검증 가능한 구조를 갖춰야 한다는 점을 체감했습니다.

또한 팀장 및 서버 담당으로 참여하며, 좋은 구조는 혼자 만드는 것이 아니라 팀원들과의 소통, 문서화, 반복 검증을 통해 완성된다는 것을 배웠습니다.

10. 다시 생각한 점

이 프로젝트는 AI 프로젝트는 아니지만, 데이터 기반 서비스에서 필요한 신뢰 기준을 배운 경험이었습니다.

다시 보면 중요한 것은 기술 스택보다 주문과 결제의 기준을 어디에 둘 것인가였습니다. 사용자가 입력한 값, 서버가 검증한 값, 주문 당시 저장된 값이 분리되어야 나중에 운영자가 같은 근거로 상황을 확인할 수 있다는 점을 배웠습니다.
