AI 생성 결과를 사용자가 이해할 수 있는 과정으로 바꾸는 인터랙션 설계

스케치 입력, AI 이미지 생성, 윤곽선 추출, C++ 재생 흐름을 분리하며 AI 결과를 단순 이미지가 아니라 사용자가 따라갈 수 있는 과정으로 만든 기록입니다.

1. 어떤 사용자 경험 문제에서 시작했는가

AI가 만든 결과물을 단순히 보여주는 것만으로는 사용자가 그 과정에 참여했다고 느끼기 어렵다고 생각했습니다.

이 프로젝트는 사용자가 그린 거친 스케치를 AI가 분석하고 재해석한 뒤, 완성된 이미지를 다시 한 획씩 그려주는 흐름을 만들려는 시도였습니다. 중요한 질문은 “AI가 무엇을 만들었는가”보다 “사용자가 AI 결과를 어떤 과정으로 이해하고 받아들이는가”에 가까웠습니다.

3. 사용자는 어떤 흐름을 지나가는가

사용자는 C++ 캔버스에서 그림을 그리고, 해당 스케치는 Python AI 파이프라인으로 전달됩니다. AI는 스케치를 분석해 결과 이미지를 생성하고, 이후 OpenCV 기반 윤곽선 추출 과정을 거쳐 다시 C++ 캔버스에서 한 획씩 재생 가능한 데이터로 변환됩니다.

사용자 스케치
→ C++ MFC Canvas
→ PNG Export
→ Python AI Pipeline
→ Stable Diffusion Result
→ Foreground / Edge Extraction
→ Stroke Data 생성
→ C++ Canvas Replay

4. 입력과 결과를 어떤 데이터로 바꿨는가

4-1. C++ 기반 드로잉 캔버스

MFC 기반 C++ 캔버스를 구성하고, 그리기 도구를 ITool 인터페이스 기반으로 분리했습니다. 이를 통해 새로운 도구를 추가할 때 캔버스 핵심 코드를 크게 수정하지 않고 확장할 수 있도록 설계했습니다.

주요 기능은 다음과 같습니다.

  • MFC 기반 드로잉 캔버스
  • Pencil, Brush, Watercolor 등 도구 확장
  • ITool 인터페이스 기반 Strategy Pattern 적용
  • 도구별 spacing, alpha 값 조정
  • Command Pattern 기반 Undo / Redo 구조

4-2. C++ / Python 파이프라인 분리

C++ 캔버스와 Python AI 로직을 하나의 프로그램 안에 강하게 묶지 않고, UDP 시그널과 파일 인터페이스를 통해 분리했습니다.

이 구조를 통해 C++은 사용자 입력과 드로잉 재생에 집중하고, Python은 AI 모델 실행과 이미지 처리에 집중하도록 역할을 나눴습니다.

주요 기능은 다음과 같습니다.

  • C++ 캔버스에서 PNG Export
  • Python AI 파이프라인에서 이미지 생성 및 처리
  • 파일 기반 stroke 데이터 교환
  • UDP 시그널로 처리 완료 알림
  • AI 모델 교체 시 Python 쪽만 수정 가능한 구조

4-3. 윤곽선 추출 및 드로잉 데이터 변환

AI 결과 이미지를 그대로 보여주는 대신, 외곽선과 내부 디테일을 추출해 다시 그릴 수 있는 데이터로 변환했습니다. 이를 통해 결과물이 단순 이미지가 아니라 “한 획씩 그려지는 경험”으로 이어질 수 있도록 했습니다.

주요 기능은 다음과 같습니다.

  • BiRefNet 기반 전경 마스크 추출
  • Canny 기반 내부 윤곽선 추출
  • 외곽선과 내부 디테일 분리
  • 드로잉 순서에 맞는 stroke 데이터 생성
  • C++ 캔버스에서 한 획씩 재생

5. 시스템은 어떤 구조로 나눴는가

AI 결과 이미지를 그대로 화면에 띄우는 방식은 구현은 쉽지만, 사용자가 “내가 그린 그림이 확장되었다”는 감각을 느끼기 어렵다고 판단했습니다.

그래서 결과 이미지를 다시 선과 획의 데이터로 변환하고, C++ 캔버스에서 한 획씩 재생하는 구조를 선택했습니다. 또한 C++과 Python을 분리해 각 계층의 책임을 명확히 했습니다.

단순 결과 이미지 출력
→ AI가 만든 그림을 사용자가 보기만 함

드로잉 재생 구조
→ 사용자의 스케치가 AI 결과로 확장되는 과정을 경험

역할 분리는 다음과 같습니다.

C++ Canvas
→ 사용자 입력, 렌더링, 드로잉 재생 담당

Python AI Pipeline
→ CLIP, Stable Diffusion, OpenCV 기반 이미지 처리 담당

UDP / File Interface
→ 두 프로세스를 느슨하게 연결

6. 내가 맡은 설계 역할

C++ 캔버스와 Python AI 파이프라인을 연결하는 구조를 담당했습니다. 특히 C++이 사용자 입력과 드로잉 재생에 집중하고, Python이 AI 모델 실행과 이미지 처리에 집중할 수 있도록 프로세스를 분리하는 데 집중했습니다.

또한 AI 결과 이미지를 OpenCV 기반 윤곽선 데이터로 변환하고, 이를 다시 C++ 캔버스에서 재생 가능한 stroke 데이터로 연결하는 흐름을 설계했습니다.

7. 구현하면서 드러난 문제

문제 1. 윤곽선이 너무 복잡하게 추출되는 문제

AI가 생성한 이미지에는 털, 배경, 질감 등 세부 정보가 많아 Canny를 그대로 적용하면 선이 과도하게 많아졌습니다. 이 상태로 드로잉을 재생하면 그림이 지저분해지고, 사용자가 의도한 형태보다 노이즈가 강조되는 문제가 있었습니다.

이를 해결하기 위해 전경 마스크와 내부 윤곽선 추출을 분리했습니다. 먼저 BiRefNet으로 전경을 분리하고, 이후 Canny를 적용해 외곽선과 내부 디테일을 단계적으로 처리했습니다.

결과적으로 외곽선이 먼저 잡히고 내부 디테일이 차례로 채워지는 자연스러운 드로잉 시퀀스를 만들 수 있었습니다.

문제 2. CLIP이 선 그림을 잘못 분류하는 문제

초기에는 CLIP의 1순위 결과를 그대로 사용했지만, line drawing 도메인에서는 사진 기반 학습 데이터와 차이가 있어 강아지나 동물 그림을 다른 클래스로 오인식하는 경우가 있었습니다.

이를 해결하기 위해 단일 프롬프트 결과에 의존하지 않고, 클래스별 여러 프롬프트를 앙상블해 평균 점수를 비교했습니다. 또한 AI가 최종 결정을 모두 내리지 않고, Top-3 후보를 사용자에게 제시해 직접 선택할 수 있도록 구조를 바꿨습니다.

결과적으로 AI 단일 판단에 의존하는 구조에서 벗어나, AI 후보 추천과 사용자 검증이 결합된 흐름을 만들 수 있었습니다.

문제 3. C++과 Python 로직이 강하게 결합될 위험

AI 모델과 캔버스 렌더링을 하나의 실행 흐름에 강하게 묶으면, 모델을 바꾸거나 캔버스 구조를 수정할 때 전체 코드가 함께 흔들릴 수 있다고 판단했습니다.

이를 해결하기 위해 UDP 시그널과 파일 인터페이스를 활용해 두 프로세스를 느슨하게 연결했습니다. 덕분에 C++은 캔버스와 렌더링을 담당하고, Python은 AI 모델과 이미지 처리를 담당하는 구조로 분리할 수 있었습니다.

8. 이 구조에서 배운 점

이 프로젝트를 통해 AI 기능을 서비스에 붙일 때 중요한 것은 단순히 모델을 실행하는 것이 아니라, AI 결과를 사용자가 경험할 수 있는 인터랙션으로 바꾸는 것이라는 점을 배웠습니다.

또한 C++과 Python을 각각의 강점에 맞게 분리하면, 실시간 입력/렌더링과 AI 모델 실행을 더 안정적으로 연결할 수 있다는 점을 경험했습니다.

10. 다시 생각한 점

이 프로젝트는 생성형 AI를 단순 이미지 생성 도구로 쓰는 것이 아니라, 사용자의 입력과 AI 결과를 다시 인터랙티브한 경험으로 연결하려는 시도였습니다.

다시 보면 핵심은 모델 성능보다 흐름 설계였습니다. 사용자가 입력하고, AI가 제안하고, 시스템이 그 결과를 다시 사람이 따라갈 수 있는 데이터로 바꾸는 과정이 있어야 서비스 경험이 만들어진다는 점을 배웠습니다.
