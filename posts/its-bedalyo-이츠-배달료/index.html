네 개의 배달 클라이언트를 하나의 TCP 규칙으로 연결하기

고객·매장·라이더·관리자 클라이언트가 같은 주문 상태를 주고받도록 8바이트 헤더와 JSON 본문을 공통 규칙으로 정리했다. 코드에서 확인한 구현과 어긋난 CmdID, 아직 검증하지 못한 서버 범위를 함께 기록한다.

  • C++
  • Qt
  • MFC
  • TCP/IP
  • JSON

배달 서비스는 화면이 네 개여도 주문은 하나의 흐름으로 움직여야 한다. 고객이 주문을 만들고, 매장이 수락하고, 라이더가 픽업과 배달을 마친다. 문제가 생기면 관리자가 같은 주문을 찾아 취소하거나 상태를 확인해야 한다.

이 프로젝트에서는 고객 화면을 Qt로, 매장·라이더·관리자 화면을 MFC로 구현했다. 화면 기술은 달랐지만 서버와 대화하는 규칙까지 달라질 수는 없었다. 그래서 먼저 맞춰야 했던 것은 UI가 아니라 TCP 패킷 계약이었다.

화면보다 통신 규칙을 먼저 맞춰야 했다

역할별 클라이언트는 서로 다른 작업을 맡는다. 고객은 매장과 메뉴를 찾고 주문을 만든다. 매장은 주문을 수락하거나 거절하고, 라이더는 픽업과 배달 완료 상태를 보낸다. 관리자는 주문 조회와 취소 같은 관리 기능을 사용한다.

기능은 달라도 같은 주문 ID와 상태를 주고받기 때문에 요청과 응답의 경계가 분명해야 했다. 특히 TCP는 한 번 보낸 데이터가 한 번의 수신으로 그대로 도착한다는 보장이 없다. JSON 본문이 나뉘어 들어오거나 여러 패킷이 붙어서 들어와도 메시지를 구분할 방법이 필요했다.

8바이트 헤더로 JSON의 경계를 만들었다

패킷 앞에는 고정 길이 헤더를 두고, 실제 데이터는 JSON 본문으로 전달했다. 헤더가 요청 종류와 본문 길이를 알려주기 때문에 수신 측은 필요한 데이터가 모두 도착할 때까지 기다릴 수 있다.

Qt 클라이언트는 들어온 데이터를 QByteArray 버퍼에 누적한 뒤 완전한 헤더와 본문이 모였을 때 패킷을 꺼낸다. MFC 클라이언트는 RecvExact 방식으로 필요한 길이만큼 반복해서 읽는다. 구현 방법은 달라도 두 클라이언트가 같은 헤더 크기와 네트워크 바이트 순서를 지키도록 맞췄다.

CmdID로 역할과 상태 변화를 나눴다

요청 종류는 CmdID 번호 대역으로 구분했다. 공통 기능, 고객, 매장, 라이더, 관리자, 서버 알림이 서로 다른 범위를 사용한다. 새 기능을 추가할 때 어느 역할의 요청인지 빠르게 찾고 충돌을 줄이려는 선택이었다.

주문 흐름도 명령 단위로 나뉜다. 고객의 주문 생성, 매장의 수락·거절, 라이더의 픽업·배달 완료, 관리자의 주문 취소가 각각 다른 요청과 응답을 사용한다. 이 구분 덕분에 화면 이벤트를 서버 요청과 연결할 수 있었지만, 프로토콜 파일이 역할별로 복사되면서 다른 문제가 생겼다.

성공 응답을 받은 뒤에 클라이언트 상태를 바꿨다

고객 클라이언트의 장바구니는 CartSession이 메모리에서 관리한다. 여러 화면을 이동해도 선택한 매장과 메뉴, 수량과 금액을 유지하고, 다른 매장의 메뉴를 담으려 할 때는 기존 장바구니를 비울지 확인한다.

주문 버튼을 누르면 빈 장바구니와 최소 주문 금액을 먼저 검사하고 주문 DTO를 만든다. 장바구니는 요청을 보낸 직후가 아니라 주문 성공 응답을 받은 뒤에 비운다. 전송이나 서버 처리에 실패했을 때 사용자가 선택한 메뉴까지 사라지는 일을 막기 위한 순서다.

복사된 프로토콜이 먼저 어긋났다

코드를 비교하면서 가장 분명하게 드러난 문제는 Global_protocol.h의 불일치였다. 관리자·매장 쪽 사본은 라이더 픽업 요청과 응답을 4002/4003으로 정의했지만, 라이더 쪽 사본은 4030/4031을 사용한다. 같은 이름의 명령이 서로 다른 숫자를 가리키면 클라이언트와 서버가 정상적으로 연결되기 어렵다.

수신 처리에도 실패 흔적이 남아 있었다. 잘못된 Signature를 만났을 때 본문을 소비하지 않고 다음 헤더를 읽으면 TCP 스트림 전체가 어긋날 수 있다. 현재 MFC 코드는 본문 크기가 허용 범위 안에 있을 때 해당 데이터를 버리고 다음 패킷을 읽도록 보완돼 있다.

주문 내역 화면처럼 골격만 있고 실제 요청 연결이 주석이나 TODO로 남은 기능도 있었다. 화면이 존재한다는 사실만으로 전체 흐름이 구현됐다고 판단할 수 없는 이유다.

이번 글에서 확인한 범위

이번 글은 저장소에 포함된 Qt와 MFC 클라이언트 코드를 정적으로 읽고 정리했다. 패킷 헤더, JSON 직렬화, 수신 버퍼, 장바구니 상태, 역할별 요청 분기는 코드에서 확인했다.

반면 서버 실행 코드와 DB 스키마, 자동화 테스트 결과는 현재 공개된 자료만으로 확인하지 못했다. README에 설명된 서버 가격 검증과 MariaDB 주문 스냅샷은 설계 목표로만 다뤘고, 구현 완료로 단정하지 않았다. 실제 빌드와 통합 실행도 수행하지 않았기 때문에 이 글의 범위는 클라이언트 구현과 통신 계약에 한정된다.

다음에는 계약을 코드로 검증해야 한다

가장 먼저 할 일은 역할별로 복사된 프로토콜 헤더를 하나의 공유 계약으로 합치는 것이다. 그다음에는 다음 조건을 자동화 테스트로 확인할 필요가 있다.

  • 헤더 크기가 항상 8바이트인지
  • 모든 클라이언트가 같은 CmdID를 사용하는지
  • 분할되거나 합쳐진 TCP 패킷을 올바르게 처리하는지
  • 주문 실패 시 장바구니 상태가 유지되는지
  • 서버가 클라이언트의 가격을 다시 검증하고 주문 시점 정보를 저장하는지

이 프로젝트에서 중요한 것은 화면 수가 아니라 여러 프로그램이 같은 상태를 어떤 규칙으로 공유하는가였다. 공통 계약을 문서에 적는 것에서 끝내지 않고 테스트 가능한 코드로 관리해야 역할이 늘어나도 주문 흐름이 흔들리지 않는다.
