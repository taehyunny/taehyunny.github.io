내부 업무 시스템을 기획할 때 먼저 생각한 것들

회사 안의 요청, 검토, 승인, 파일, 기록 흐름을 하나의 업무 시스템으로 묶기 위해 어떤 관점이 먼저 필요했는지 정리한 글입니다.

1. 왜 내부 업무 시스템을 생각하게 되었는가

회사 안의 일은 대부분 누군가의 요청에서 시작된다.

자료를 요청하고, 확인을 부탁하고, 승인받고, 파일을 전달하고, 다시 수정하고, 완료 여부를 남긴다. 겉으로 보면 단순한 커뮤니케이션처럼 보이지만, 실제로는 여러 사람이 같은 일을 다른 방식으로 기억하고 처리하는 문제가 생긴다.

처음에는 이런 흐름을 더 빠르게 처리하는 도구를 만들고 싶었다. 하지만 정리하다 보니 속도보다 먼저 필요한 것은 “업무가 어떤 상태에 있고, 누가 다음 판단을 해야 하며, 어떤 자료가 최종 근거인지 알 수 있는 구조”라는 생각이 들었다.

그래서 이 시스템은 단순한 요청 게시판이나 파일함이 아니라, 회사 내부 업무가 흘러가는 방식을 정리하는 운영 플랫폼에 가깝게 바라보게 되었다.

2. 문제는 기능 부족보다 흐름의 불명확함이었다

업무 도구를 만들 때 처음 떠올리기 쉬운 것은 기능 목록이다.

  • 요청 등록
  • 파일 업로드
  • 승인
  • 댓글
  • 알림
  • 검색

물론 이런 기능은 필요하다. 하지만 기능을 먼저 만들면 각 기능이 따로 움직이기 쉽다. 요청은 요청대로 남고, 파일은 파일대로 흩어지고, 승인은 메신저나 구두 확인으로 끝나고, 나중에 왜 그렇게 결정했는지 다시 찾기 어려워진다.

내가 더 중요하게 본 문제는 기능의 수가 아니라 흐름의 연결이었다.

요청이 들어왔다
→ 누가 검토해야 하는가
→ 어떤 자료를 봐야 하는가
→ 어떤 판단이 남아야 하는가
→ 완료 후 무엇이 기록으로 남는가

이 흐름이 명확하지 않으면 시스템이 있어도 사람은 다시 메신저, 구두 전달, 개인 폴더에 의존하게 된다.

3. 모든 업무를 하나의 공통 요청 단위로 바라보기

내부 업무는 종류가 다양하다. 자료 요청, 비품 구매, 영상 제작, 개발 요청, 회계 전달, 일정 조율, 외부 문의처럼 이름은 다르지만 기본 흐름은 비슷하다.

누군가 요청하고, 담당자가 확인하고, 필요하면 검토와 승인을 거치고, 관련 파일과 의견이 붙고, 마지막에는 완료 여부가 남는다.

그래서 처음부터 업무별로 화면과 로직을 따로 만드는 것보다, 공통 요청 단위를 먼저 생각하는 편이 더 안전하다고 봤다.

업무마다 다른 것은 상세 입력 항목이다. 하지만 공통으로 필요한 것은 대체로 비슷하다.

  • 요청자
  • 담당 부서 또는 담당자
  • 현재 상태
  • 관련 파일
  • 검토 의견
  • 승인 또는 반려 이력
  • 완료 기록

이 공통 구조가 있으면 새로운 업무가 추가되어도 전체 시스템의 원칙은 흔들리지 않는다. 기능을 계속 덧붙이는 것이 아니라, 같은 업무 운영 원칙 안에서 모듈을 확장할 수 있다.

4. 승인과 검토는 다르게 다뤄야 한다

업무 시스템을 설계할 때 검토와 승인을 같은 의미로 처리하면 위험하다.

검토는 의견을 남기는 행위에 가깝고, 승인은 책임 있는 최종 판단에 가깝다. 누군가 “검토했습니다”라고 말한 것과 “진행해도 됩니다”라고 결정한 것은 다르다.

이 차이가 시스템에 반영되지 않으면 업무가 애매한 상태로 실행될 수 있다.

그래서 승인 구조를 생각할 때는 버튼 하나보다 책임의 경계를 먼저 봐야 한다.

  • 누가 검토 의견을 남길 수 있는가
  • 누가 보완 요청을 할 수 있는가
  • 누가 최종 승인할 수 있는가
  • 승인 전에는 어떤 상태로 넘어가면 안 되는가
  • 나중에 그 판단을 어떻게 확인할 수 있는가

결국 승인 기능은 단순한 상태 변경이 아니라, 책임과 기록을 남기는 장치다.

5. 파일 관리는 저장보다 추적이 중요하다

업무에서 파일은 결과물이자 근거다. 하지만 파일을 단순히 업로드할 수 있게 만드는 것만으로는 부족하다.

중요한 것은 이 파일이 어떤 요청과 연결되어 있는지, 누가 올렸는지, 어떤 버전이 최종본인지, 누가 내려받았는지 확인할 수 있는 구조다.

특히 내부 문서나 증빙 자료는 파일 경로가 그대로 노출되면 안 된다. 사용자는 “다운로드” 버튼을 누르지만, 시스템 안에서는 권한을 확인하고, 기록을 남기고, 실제 저장 위치는 숨겨야 한다.

파일 관리에서 내가 중요하게 본 원칙은 세 가지다.

  • 파일 원본과 업무 메타데이터를 분리한다.
  • 다운로드는 권한 확인 후 허용한다.
  • 파일 접근 기록은 나중에 확인할 수 있게 남긴다.

이렇게 보면 파일 업로드 기능도 단순 편의 기능이 아니라 내부 통제와 업무 추적의 일부가 된다.

6. 권한은 화면이 아니라 서버 기준으로 생각해야 한다

내부 시스템에서 권한은 메뉴를 숨기는 문제로 끝나지 않는다.

화면에서 버튼이 보이지 않더라도, 서버가 요청을 받아들이면 권한 통제는 실패한 것이다. 그래서 권한은 UI보다 서버 규칙을 먼저 설계해야 한다.

또한 권한은 단순히 관리자와 일반 사용자로 나누기 어렵다. 같은 직원이라도 소속 부서, 맡은 업무, 요청자인지 처리자인지에 따라 볼 수 있는 정보가 달라진다.

내가 생각한 기준은 단순하다.

이 사용자가 이 업무를 볼 이유가 있는가?
이 사용자가 이 파일을 받을 이유가 있는가?
이 사용자가 이 상태를 바꿀 책임이 있는가?

이 질문에 답할 수 있어야 내부 업무 시스템이 안전해진다.

7. AI 자동화는 판단을 대체하기보다 정리를 돕는 쪽이 맞다

이런 시스템을 생각하다 보면 AI를 어디에 붙일 수 있을지도 자연스럽게 떠오른다.

하지만 내부 업무 시스템에서 AI가 모든 판단을 대신하는 것은 적절하지 않다. 특히 승인, 회계, 외부 문의, 계약처럼 책임이 필요한 영역에서는 사람이 마지막 판단을 해야 한다.

대신 AI가 잘할 수 있는 일은 따로 있다.

  • 요청 내용을 요약한다.
  • 누락된 정보를 질문으로 정리한다.
  • 관련 파일을 분류한다.
  • 반복 문서를 초안으로 만든다.
  • 처리 이력을 읽고 다음 액션을 제안한다.
  • 공공데이터나 내부 데이터를 바탕으로 검토 자료를 정리한다.

즉 AI는 결재권자가 아니라 업무 정리자에 가깝다. 사람이 더 나은 판단을 할 수 있도록 자료를 정돈하고, 누락을 발견하고, 반복 작업을 줄이는 역할이 더 현실적이다.

8. 처음부터 크게 만들지 않는 이유

내부 업무 시스템은 욕심을 내면 금방 커진다.

요청, 결재, 파일, 일정, 회계, 외부 문의, 강사 관리, 프로젝트 관리까지 모두 넣고 싶어진다. 하지만 처음부터 모든 기능을 만들면 핵심 흐름이 검증되기 전에 구조가 복잡해진다.

그래서 1차 목표는 작아야 한다.

내 기준에서 처음 검증해야 할 것은 다음 정도다.

  • 사용자가 요청을 등록할 수 있는가
  • 담당자가 요청을 확인할 수 있는가
  • 검토와 승인 흐름이 분리되는가
  • 파일이 요청과 연결되는가
  • 처리 이력이 남는가
  • 권한 없는 사용자가 접근하지 못하는가

이 흐름이 안정되면 그다음에 일정, 회계, 외부 문의, 강의 매칭 같은 확장을 붙이는 편이 낫다.

9. 전략기획 관점에서 얻은 생각

이 문서를 정리하면서 느낀 것은, 전략기획은 단순히 아이디어를 내는 일이 아니라 업무가 실제로 돌아갈 구조를 만드는 일이라는 점이다.

좋은 시스템은 화면이 많은 시스템이 아니라, 사람들이 같은 기준으로 요청하고 판단하고 기록할 수 있게 해주는 시스템이다.

내부 업무 시스템을 기획할 때 중요한 질문은 “어떤 기능을 만들까”보다 “이 회사의 업무가 어떤 규칙으로 흘러야 할까”에 가깝다.

그리고 AI 자동화는 그 규칙 위에 올라가야 한다. 규칙이 없는 업무에 AI를 붙이면 더 빠르게 혼란스러워질 수 있다. 반대로 요청, 승인, 파일, 로그, 권한의 흐름이 잡혀 있으면 AI는 그 위에서 문서 정리, 누락 확인, 데이터 기반 검토를 도와줄 수 있다.

10. 다음에 더 생각해볼 것

다음 단계에서는 실제 구현보다 먼저 몇 가지를 더 정리하고 싶다.

  • 어떤 요청 유형을 1차 MVP에 넣을 것인가
  • 승인과 검토를 어떻게 최소 단계로 유지할 것인가
  • 파일 보관 규칙을 얼마나 단순하게 시작할 것인가
  • AI가 생성한 요약과 사람이 승인한 기록을 어떻게 구분할 것인가
  • 공공데이터 기반 서비스 기획과 내부 업무 시스템을 어떻게 연결할 것인가

이 프로젝트는 개발 프로젝트이기도 하지만, 더 크게 보면 업무 흐름을 설계하는 연습이다. 전략기획 관점에서 시스템을 바라보는 첫 번째 기준은 “사람이 일하는 방식을 더 명확하게 만드는가”라고 생각한다.
